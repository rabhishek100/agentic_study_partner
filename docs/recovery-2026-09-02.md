# Local recovery, 2026-09-02

## What was actually wrong

The reported state was a rolled-back database: 3 books, 2 videos, 0 courses,
0 evidence units. That was a symptom, not the fault.

Colima's VM has two virtual disks. The second one, `vdb1`, holds
`/var/lib/docker` — every image, container layer and volume — and it had been
sized at 30 GB, filled, and **aborted its ext4 journal**:

```
EXT4-fs error (device vdb1): ext4_journal_check_start:84: Detected aborted journal
JBD2: I/O error when updating journal superblock for vdb1-8
```

From then on the filesystem returned `EIO` on reads. `docker images` failed,
container logs were unreadable, and Postgres — still running, still reporting
healthy — could only see the parts of its own volume that still read back.
Hence three books where there were fifty-six.

A normal Docker Desktop restart did not help, and could not: **Docker Desktop
was not the runtime.** The active context was `colima`. The corruption was
inside the Colima VM the whole time.

## What was done

The VM was destroyed and rebuilt with a 60 GB data disk, after every recovery
artifact had been copied to a second location and checksum-verified. On the
repaired filesystem the full corpus was readable again, and a `pg_dump` of it
completed without a single unreadable page.

That dump was compared against the canonical 511 MB corpus backup restored
into a scratch database. Content hashes matched exactly for books, nodes,
content blocks, chunks, auth users, video ids and titles, lecture ordering,
transcript text, and evidence ids and text. The only differences were mutable
state columns, where the live database was *newer*. Nothing had been lost.

## Course versus video ingestion parity

There is one contract, in `docs/video-ingestion-quality-contract.md`, and a
course lecture references the same canonical video and ingestion version the
standalone experience uses. Structurally, parity holds: course membership adds
ordering and a budget and nothing else.

In *completeness*, neither path is finished:

| State | Videos | Of which course lectures |
|---|---|---|
| Fully ready | 2 | 1 |
| Available with limitations | 2 | 2 |
| Processing | 17 | 17 |

The funnel across all 21 videos: 10 acquired, 8 through the visual stages,
5 published.

**Two lectures are mislabelled.** Lectures 2 and 14 are marked `degraded`,
which the contract defines as published and answerable, and both hold **zero
evidence units, zero embeddings and zero transcript segments**. They are 0.2
minutes long and cost $0.001 each — acquisition stubs, not lectures. They
cannot answer anything, and should be `failed` or `blocked`. A course question
that selects one gets no evidence from it and is not told why: it is not
reported in `excluded_video_ids`, because that list only covers versions that
were never published.

## Verified working

- Books, Papers, Videos and Courses all list and open through the API as
  `human@rockfortrobotics.com`.
- Source PDFs download and parse: 296, 550 and 45 pages on three samples.
- A grounded course question returns an answer with correct lecture identity
  and exact timestamps, over both modalities:
  `[S3] lecture 12 "Lecture 13: Spanner" @65:26 visual_frame`,
  `[S2] … @39:10 transcript`. Cost $0.000377.
- The frontend production build serves and gates on sign-in.
- Full backend suite 1,737 passed / 2 skipped / 0 failed; frontend 621 tests,
  typecheck, design-token lint, production build; 46/46 migrations on a fresh
  database; a full clean restore from the golden dump reproduced exact parity.

## Not verified

- **Cross-lecture retrieval over more than one lecture.** The mechanism is
  covered by tests and worked live, but only one lecture in the corpus holds
  evidence, so multi-lecture grounding cannot be demonstrated on real data
  until more lectures are ingested.
- **Worker resume**, for the same reason: no worker was started, because
  re-ingestion was deliberately not run.
- **The UI past the sign-in gate**, which needs the account owner's own
  credentials.

## Two hazards worth fixing before the next run

**1. The test suite deletes book sources.** Tests call the Storage HTTP API
with the service-role key and delete `book-sources` objects. The Storage
service always serves the `postgres` database, so pointing tests at a separate
database does not protect it — during this recovery the suite removed 52 of
the 54 restored PDFs, and the failure only surfaced later as a 404 on a book's
source. Either the tests need their own bucket, or the suite must not run
against a stack holding the real corpus.

**2. The test suite claims real ingestion jobs.** Run against the corpus
database, it claimed 11 jobs under test worker ids and moved a queued job to
failed. Content was untouched; orchestration state was not. Tests now run
against `study_partner_test`, which is faster (65s versus 178s) and green.
